## Blocking issue — P/N navigation (FA16 still crashing)

### Symptom
When user types `P` or `N`, the Topic:
1. Updates DateContext via `Text(DateAdd(Topic.DateContext, -1/+1, TimeUnit.Days), "yyyy-MM-dd")`
2. Loops back to C1_Set_DateContext
3. Calls C2_Call_FlowA_Initial with InSelectedNumber = `" "` (single space)

Flow A then:
- FA02 initialises `varInSelectedNumber` — no default value in code, reads from trigger
- FA15 Compose IsSelectionMode: `not(empty(trim(variables('varInSelectedNumber'))))` — this is returning `true` for the space, routing into FA17 True branch
- FA16 Compose SelectedIndex: expression is now `if(equals(trim(variables('varInSelectedNumber')), ''), 0, sub(int(trim(variables('varInSelectedNumber'))), 1))` — but still crashing with `int` invalid parameter

### Root cause analysis
The FA16 expression fix is confirmed saved in the JSON code view. However runs at 10:19 PM and 10:44 PM are still showing the old error — it's unclear whether the fix had fully propagated or whether there's a deeper issue with the value arriving.

**Key suspect:** FA15 is returning `true` for `" "` (space). If `trim(" ")` is genuinely returning `""` then `not(empty(""))` = `not(true)` = `false`, and FA17 should go to the False (else) branch — skipping FA16 entirely. But FA17 is routing to True, meaning FA15 must be returning something other than expected.

Possible explanations:
1. The space character in the Topic's C2 InSelectedNumber field is not a regular ASCII space — it may be a non-breaking space or other Unicode character that `trim()` doesn't remove
2. The FA16 fix hadn't propagated at test time — the code view showed the correct expression but the runtime was still using the old version
3. Some other value is reaching `varInSelectedNumber` that isn't empty after trim

### Recommended next session investigation

**Step 1 — Check FA03A DEBUG RawInputs output** for a P/N call in Activity. This will show exactly what value `triggerBody()?['text_1']` is receiving. This is the ground truth — if it shows `" "` (space) or `""` (empty) we know the Topic is sending correctly.

**Step 2 — Check FA15 output** in a failed run's Activity view. Click FA15 in the activity trace to see what boolean value it actually output. If it's showing `true` for a space input, the trim isn't working.

**Step 3 — If the fix just hadn't propagated:** After the connection refresh, do a fresh test and check the Activity for a post-10:44 PM run. The FA16 expression in the JSON is correct — it may simply work now.

**Step 4 — Alternative fix if space is the problem:** Change the Topic's C2 InSelectedNumber value from `" "` (space) back to `Blank()` formula, OR change FA15's expression to also check for a specific numeric pattern:
```
and(not(empty(trim(variables('varInSelectedNumber')))), not(equals(trim(variables('varInSelectedNumber')), ' ')))
```

**Step 5 — Cleanest architectural fix:** In the Topic, instead of passing `" "` for the initial/P/N calls, pass a literal string like `"0"` or `"NONE"`, and update FA15 to check for that sentinel value:
```
not(or(empty(trim(variables('varInSelectedNumber'))), equals(trim(variables('varInSelectedNumber')), 'NONE')))
```
This is more explicit and immune to whitespace encoding issues.
